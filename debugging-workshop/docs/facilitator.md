# 運営向け進行資料（公開用・解答なし）

目的は、期待と実際の比較、仮説を確かめる調査、テスト、AIの検証を体験することです。未完了のチームにも調査成果を共有してもらいます。完全な原因一覧や修正済みコードはこのリポジトリに保存しません。作成時のCodex最終報告を運営者だけが保管してください。

## 開催前の準備

- Windows実機で[README](../README.md)の「フォルダーを開く → ビルド → Ctrl+F5 → 任意入力 → CTest」を3課題分試す。日本語表示とCtrl+F5のコンソール保持も確認。
- VSの必要ワークロード、CMake/Ninja/MSVC、インターネット・AIアカウントの利用可否を事前確認。インストール時間は120分に含めない。
- 配布版ではビルド成功・3つのCTestが失敗することを確認。失敗を「環境不良」と取り違えない。[検証記録](validation.md)の基準と比較する。
- 初心者を含む2～4人のチームに分ける。1台の操作PCと、検索・記録用の端末を用意すると進めやすい。
- 記録テンプレートを課題ごとに配布。共同編集メモや紙でもよい。
- 段階AではCopilot等の生成AI補完も無効にする。検索結果のAI要約は利用せず、通常のWebページを参照する。
- ヒントは公開されているためアクセス制御はない。案内された段階だけ開くルールを共有する。
- 参加者の修正版はチームのローカルまたは非公開の提出先で扱う。公開リポジトリ・PR・Issueへ解答を投稿しない。
- 各チームにAIアクセスを用意できない場合は運営端末で順番に同じ時間だけ利用する。利用できなかったチームは比較を「未実施」と記録し、評価で不利益にしない。

## 120分の進行

| 時間 | 内容 | 運営の声かけ・終了時の成果 |
|---|---|---|
| 0～10分 | 企画説明・チーム分け | 期待／実際の読み方、AIの利用段階、役割を説明。HPの起動まで確認 |
| 10～30分 | 初級：HP計算 | 最初の3分で仕様と期待値を読む。入力を変えた観察と仮説を残す |
| 30～65分 | 中級：追尾 | 役割交代。最初の5分で座標と1ステップを手計算。最後の5分で記録 |
| 65～95分 | 上級：当たり判定 | 役割交代。最初の5分で円と距離を図示。未修正でも誤判定の条件を言語化 |
| 95～110分 | AIで再調査・比較 | 95～98分で人間段階の記録・コード・ログを保存。98～106分で1課題をAIで再調査。106～110分で提案をテストして比較 |
| 110～120分 | 結果共有・振り返り | 各チーム1分程度で「仮説・証拠・AIをどう検証したか」を発表。多数なら隣接チームと共有後に代表発表 |

10～95分は段階Aです。Web検索・C++リファレンス・デバッグ出力・デバッガを使えますが、AIによる直接的な問題解決は禁止します。95分で段階Bへ切り替えます。

本企画の比較対象は厳密には**「人間のみ」と「人間＋AI」**です。同じ課題を再調査するため、学習時間の差もあります。AI単独の性能比較や速度の優劣を科学的に示すものではありません。

## ヒントの提示

ヒント利用に減点は設けません。内容を答える前に「入力・期待・実際を説明できますか」と尋ねます。

1. 3～5分間、次に試すことが決まらない、または本人が希望したらヒント1。
2. 観察はできたが調べ方が決まらない状態がさらに3～5分続いたらヒント2。
3. 値を調べても仮説を絞れない、残り5分程度、または本人が希望したらヒント3。

各段階の後に、チームが自分で次の実験を決める時間を設けます。完成コードは提示しません。ヒント後に原因だけ説明できた場合も評価します。

## 役割分担

- 操作担当：入力、編集、実行。初心者も少なくとも1回担当する。
- 観察担当：仕様と実行結果の差を探し、期待値を手計算する。
- 調査担当：検索、リファレンス、デバッガを使う。
- 記録担当：仮説・根拠・テスト結果・AI前後の差を記録する。

2人なら操作＋記録、観察＋調査に分けます。課題ごとに交代します。経験者は先にコードを書くのではなく、初心者が次に確かめる値を選べるよう質問します。AI段階では提案を読む人と検証する人を分けると有効です。

## 採点（100点・速度による加点なし）

各課題25点、3課題で75点です。

| 観点 | 1課題あたりの点数 | 基準 |
|---|---:|---|
| 観察 | 5 | 入力・期待・実際を再現可能な形で示した |
| 仮説と切り分け | 5 | 仮説を立て、条件を変えて検証した |
| 原因説明 | 5 | 仕様とコードの関係を根拠付きで説明した。未修正でも可 |
| 修正 | 5 | 仕様に合う修正。部分的に改善した場合は1～4点 |
| 検証 | 5 | 公開テストの結果と、自分たちの追加ケースを説明した。公開テストのみは3点まで |

残り25点：AIへの質問に仕様と観察を含める5点、提案を実行・追加ケースで確かめる10点、人間段階との差を記録する5点、根拠を共有する5点。AI利用できないチームは同じ観点で「他チームの提案との比較」を行い、AI比較は未実施と明示します。

正解コードとの一致や修正速度では採点しません。テストの期待値を変えて通した場合は修正・検証の得点対象外です。公開テストを維持したまま、別の追加テストを用意することは歓迎します。同点なら順位を無理につけず、観察賞・検証賞などを設けても構いません。

## 進行が遅れた場合

- 環境の問題は運営が対応し、チームは仕様を紙で読んで期待値を考える。
- 時間になったら未修正でも次の課題へ。コードを戻す必要はなく、課題は独立している。
- 各課題で「失敗する入力1つ、成功する入力1つ、仮説1つ」の記録を最低限の目標にする。
- 上級は図と期待値の説明だけでもよい。AI段階は未解決の1課題に絞る。
- 早く終わったチームは追加ケースを作り、他チームへ解答を伝えず調査方法を助言する。

## よくある質問

| 質問 | 対応 |
|---|---|
| 最初からテストが失敗している | 仕様と実装の違いを探す教材なので正常。まず成功するケースと比較 |
| C++の文法が分からない | `return`、`if`、関数引数、構造体など必要な単語を一つずつ検索。共通UIまで理解する必要はない |
| 直しても一部が失敗する | 再ビルドしたか確認。その後、別の入力群や境界条件を調べる |
| テストを通すために期待値を変えてよいか | 不可。仕様を満たす実装へ修正。期待値の疑問は運営へ確認 |
| AIの説明はもっともらしい | 実行して確認し、仕様にない挙動を追加していないか調べる。未確認ならそう記録 |
| AIが全部修正してしまった | 説明できる変更だけ採用し、入力を変えて再確認。提案の量は加点しない |
| CTestに日本語が出ない | `*_tests.exe` を直接実行し、期待と実際を読む。READMEの文字化け対策も参照 |
| 初心者が発言できない | 操作と期待値の説明を任せ、経験者には問いかけ役を依頼 |

AIへの質問例：

> C++17の教材です。仕様は（仕様）、入力は（値）、期待は（値）、実際は（値）です。私たちは（仮説）と考え、（調査）を試しました。原因を切り分ける次の調査方法を提案してください。公開テストや仕様は変更せず、外部ライブラリは追加しないでください。

コードを送る場合も、参加者自身の秘密情報・アカウント情報を含めません。
